# Plano — Pré-requisitos para SDD (Spec-Driven Development)

**Data:** 2026-10-06
**Status:** Executado

> Este documento registra a implantação inicial. O processo operacional atual,
> incluindo DoR/DoD, artefatos e handoffs, está em
> `docs/process/sdd-workflow.md` e prevalece em caso de divergência.

## Objetivo

Organizar o projeto com agentes de IA por etapa do ciclo SDD, garantindo um fluxo de planejamento, desenvolvimento e validação controlado.

## Decisões

- Ciclo: **Spec → Plano → Implementação → Validação**, com um agente por etapa.
- Templates em `docs/features/` e `docs/decisions/` definem o formato das entregas de cada fase.
- Os antigos briefings em `.agents/roles/` são substituídos por agentes nativos em `.opencode/agents/`.
- Skills continuam em `.agents/skills/` e são referenciadas pelos agentes.
- Documentação fica embutida em cada agente (sem agente separado).
- Testes ficam com agente dedicado (`test-engineer`).

## Agentes (`.opencode/agents/`)

| Agente | Fase | Função |
| --- | --- | --- |
| `sdd-orchestrator` | — | Coordena fases, checa gates em `docs/features/` e delega |
| `product-spec` | Spec | Produz especificação verificável em `docs/features/` |
| `tech-planner` | Plano | Faz perguntas até o plano estar completo; só encerra com aprovação |
| `architecture-review` | Plano/Mudança | Revisa limites de serviço, dados, contratos e eventos |
| `backend-dev` | Implementação | Serviços Node/TS com arquitetura hexagonal |
| `angular-dev` | Implementação | PWA Angular mobile-first |
| `test-engineer` | Teste | Estratégia, escrita e execução de testes |
| `feature-validator` | Validação | Confere critérios de aceite, contratos, docs e ADR |
| `code-reviewer` | Pós-PR | Revisa por lentes essenciais e adiciona lentes conforme o risco |

## Gates entre fases

1. Spec: `AC-*` verificáveis, zero decisão bloqueante e aprovação do usuário.
2. Plano: tarefas `T-*` rastreáveis, aprovação do usuário e revisão
   arquitetural persistida quando cruza serviços.
3. Implementação: tarefas concluídas, testes auditados e contratos documentados.
4. Validação: `VALIDATION.md` com evidência por `AC-*` e aprovação técnica do
   `feature-validator`.

## Refinamento — delegação por tarefa em paralelo

**Data:** 2026-10-06
**Decisão revisada:** o `sdd-orchestrator` delega uma chamada por tarefa do
`PLAN.md`, sequencialmente por padrão.

Regras:
- No máximo duas tarefas independentes, sem dependência e com arquivos
  disjuntos rodam em paralelo.
- Tarefas que tocam os mesmos arquivos ou módulos de um serviço rodam em sequência, para evitar conflitos de edição.
- O paralelismo vale **dentro de uma fase**; os gates do SDD não mudam. Spec e plano continuam sequenciais e dependem de respostas do usuário, portanto não são paralelizáveis.
- O orquestrador acompanha a conclusão de cada tarefa e só avança de fase quando o gate estiver cumprido.

## Fluxo de git

**Data:** 2026-10-06
**Decisões:**

- Commits pequenos por tarefa ou mudança coerente; gates são estado documental.
- **Branch por feature**: `feature/<nome-da-feature>`, criada na aprovação do plano.
- **Push, PR e merge** exigem aprovações explícitas e separadas do usuário.
- PR é o caminho principal de integração quando existe remoto; merge local
  `--no-ff` é fallback para repositório sem remoto.
- Commits em Conventional Commits com escopo; corpo referencia `T-*`, `AC-*` e
  `docs/features/<feature>/`.
- Somente o `sdd-orchestrator` executa git; subagents não commitam.
- Trabalho que não é feature (setup, docs de processo) vai direto ao `master`.
- Skill: `.agents/skills/git-workflow/SKILL.md`.

**Data:** 2026-10-06
**Decisão revisada — PR-first:** após o push aprovado, o orquestrador oferece
abrir PR e pede nova aprovação. Não faz merge local antes do PR.

## Revisão de PR (consultiva)

**Data:** 2026-10-06
**Decisões:**

- Novo agente `code-reviewer` (`mode: primary`), invocado **manualmente pelo usuário** com o número do PR ou a branch (`feature/<nome>`).
- A revisão é **consultiva**: emite veredito (`APPROVE` / `REQUEST CHANGES` / `COMMENT`) que informa a decisão do usuário. Não bloqueia o merge, não edita código, não roda git mutante e não faz merge.
- Lentes essenciais em paralelo: `reviewer-security`,
  `reviewer-requirements` e `reviewer-regression`. Testes, arquitetura e
  performance entram conforme o risco do diff. Todos são read-only por
  permissão e instrução.
- Procedimento compartilhado (coleta do diff via `gh pr diff` com fallback em `git diff`, taxonomia de severidade 🔴🟠🟡🔵, formato do parecer por lente e regras de consolidação) na skill `code-review` (`.agents/skills/code-review/SKILL.md`).
- O relatório é apresentado no chat (não é persistido em arquivo).
- A decisão de merge continua exigindo aprovação explícita do usuário (regra do `git-workflow` não mudou).
