# Plano — Pré-requisitos para SDD (Spec-Driven Development)

**Data:** 2026-10-06
**Status:** Executado

## Objetivo

Organizar o projeto com agentes de IA por etapa do ciclo SDD, garantindo um fluxo de planejamento, desenvolvimento e validação controlado.

## Decisões

- Ciclo: **Spec → Plano → Implementação → Validação**, com um agente por etapa.
- Templates em `docs/features/` e `docs/decisions/` definem o formato das entregas de cada fase.
- Os antigos briefings em `.agents/roles/` são substituídos por agentes nativos em `.opencode/agents/`.
- Skills continuam em `.agents/skills/` e são referenciadas pelos agentes.
- Documentação fica embutida em cada agente (sem agente separado).
- Testes ficam com agente dedicado (`test-engineer`).

## Agentes (`.opencode/agents/`)

| Agente | Fase | Função |
| --- | --- | --- |
| `sdd-orchestrator` | — | Coordena fases, checa gates em `docs/features/` e delega |
| `product-spec` | Spec | Produz especificação verificável em `docs/features/` |
| `tech-planner` | Plano | Faz perguntas até o plano estar completo; só encerra com aprovação |
| `architecture-review` | Plano/Mudança | Revisa limites de serviço, dados, contratos e eventos |
| `backend-dev` | Implementação | Serviços Node/TS com arquitetura hexagonal |
| `angular-dev` | Implementação | PWA Angular mobile-first |
| `test-engineer` | Teste | Estratégia, escrita e execução de testes |
| `feature-validator` | Validação | Confere critérios de aceite, contratos, docs e ADR |

## Gates entre fases

1. Spec: template preenchido, dúvidas bloqueantes registradas como em aberto.
2. Plano: tech-planner confirmou com o usuário; arquitetura revisada quando cruza serviços.
3. Implementação: testes escritos/rodando; contratos documentados.
4. Validação: critérios de aceite verificados; ADR registrada se aplicável.

## Refinamento — delegação por tarefa em paralelo

**Data:** 2026-10-06
**Decisão:** o `sdd-orchestrator` delega uma chamada de subagente por tarefa do `PLAN.md`, em vez de uma chamada por fase inteira.

Regras:
- Tarefas independentes (escopos de arquivo distintos, ex.: serviço backend e tela Angular) rodam em paralelo, via subagentes em background.
- Tarefas que tocam os mesmos arquivos ou módulos de um serviço rodam em sequência, para evitar conflitos de edição.
- O paralelismo vale **dentro de uma fase**; os gates do SDD não mudam. Spec e plano continuam sequenciais e dependem de respostas do usuário, portanto não são paralelizáveis.
- O orquestrador acompanha a conclusão de cada tarefa e só avança de fase quando o gate estiver cumprido.

## Fluxo de git

**Data:** 2026-10-06
**Decisões:**

- Um commit por **gate** cumprido do SDD.
- **Branch por feature**: `feature/<nome-da-feature>`, criada na aprovação do plano; merge `--no-ff` ao `master` após o gate de validação.
- **Push somente com aprovação explícita do usuário**; o orquestrador apresenta o resumo antes.
- Commits em Conventional Commits com escopo (`feat(auth): ...`, `docs(list): ...`); corpo referencia `docs/features/<feature>/` e os critérios de aceite atendidos.
- Somente o `sdd-orchestrator` executa git; subagents não commitam.
- Trabalho que não é feature (setup, docs de processo) vai direto ao `master`.
- Skill: `.agents/skills/git-workflow/SKILL.md`.
